Mày đóng vai trò Tech Lead/Software Engineer phụ trách triển khai và kiểm thử đồ án AI Tutor của tao.

BỐI CẢNH DỰ ÁN
Tên đề tài: “Xây dựng AI Tutor hỗ trợ học môn Lập trình WinForms cơ bản”.

Đây là giai đoạn CP4 – Triển khai và CP5 – Kiểm thử. Phần phân tích và thiết kế đã hoàn thành. Không được quay lại thay đổi kiến trúc, phạm vi hoặc thêm tính năng ngoài MVP nếu không có lỗi thực tế bắt buộc phải sửa.

Hãy đọc kỹ tài liệu thiết kế hiện tại của dự án trước khi thực hiện:
- Chương 1: phạm vi, mục tiêu, chức năng bắt buộc.
- Chương 2: Use Case, Activity, Sequence, ERD, kiến trúc, API, Backend.
- Đặc biệt phải bám đúng các chức năng SV01–SV07 và AI01–AI07.

→ Output

CƠ CHẾ ADAPTIVE ĐÃ CHỐT

Student Model hiện tại phân loại người học ở mức cơ bản:
- Yếu
- Trung bình
- Khá

Dựa trên các tín hiệu như:
- số lần hỏi lại
- lỗi gặp phải
- kết quả tương tác/bài tập

Sau đó điều chỉnh:
- mức độ giải thích
- mức độ gợi ý
- cách diễn đạt
- độ khó hỗ trợ

Không được biến Adaptive Response thành một hệ thống machine learning phức tạp nếu code hiện tại chưa có. Chỉ triển khai đúng mức cơ bản đã thiết kế.

BỘ TEST CASE PHẢI CÓ ÍT NHẤT CÁC NHÓM:

A. Authentication
- đăng nhập đúng
- sai username
- sai password
- dữ liệu rỗng

B. AI Tutor
- câu hỏi WinForms hợp lệ
- câu hỏi C# hợp lệ
- câu hỏi ngoài phạm vi
- câu hỏi không rõ
- câu hỏi cần kiến thức từ Knowledge Base
- câu hỏi cần nguồn

C. RAG
- tài liệu hợp lệ
- retrieval tìm được nội dung liên quan
- retrieval không tìm được nội dung
- kiểm tra context được đưa vào LLM
- kiểm tra citation/source

D. Upload
- PDF hợp lệ
- DOCX/TXT nếu hệ thống hỗ trợ
- file rỗng
- file sai định dạng
- tài liệu ngoài phạm vi
- tài liệu được lưu và truy xuất lại

E. Code Analysis
- code C# đúng
- code có lỗi syntax
- code có lỗi logic
- code WinForms có lỗi event
- code quá dài/không hợp lệ
- yêu cầu giải thích code

F. Student Model
- user mới chưa có dữ liệu
- user có lịch sử tương tác
- learning progress được cập nhật
- concept được cập nhật
- evidence_count hoạt động đúng

G. Adaptive Response
- trạng thái Yếu
- trạng thái Trung bình
- trạng thái Khá
- cùng một câu hỏi nhưng mức hỗ trợ khác nhau
- kiểm tra hệ thống không thay đổi trạng thái chỉ vì một interaction đơn lẻ nếu thiết kế hiện tại không cho phép.

H. History
- tạo session
- lưu interaction
- xem lại session
- dữ liệu đúng user
- không truy cập nhầm dữ liệu user khác.

QUY TẮC KHI TÌM VÀ SỬA BUG
==================================================

Không được đoán.

Mỗi bug phải xác định:

1. Chức năng bị lỗi
2. Input gây lỗi
3. Expected result
4. Actual result
5. Log/error
6. File/module gây lỗi
7. Nguyên nhân gốc
8. Cách sửa
9. Kiểm thử lại
10. Regression test

Nếu chưa đủ dữ liệu để xác định nguyên nhân:
→ nói rõ “Chưa đủ dữ liệu để xác minh nguyên nhân”
→ chỉ ra chính xác cần log/code nào.

Không được nói “có vẻ”, “chắc là”, “khả năng cao” rồi tự sửa code.

==================================================
QUY TẮC CODE
==================================================

- Không phá API đang hoạt động.
- Không đổi database schema nếu không thực sự cần.
- Nếu phải thay đổi schema, phải chỉ rõ ảnh hưởng.
- Không hard-code API key.
- Không đưa secret vào GitHub.
- Kiểm tra .env và .gitignore.
- Xử lý exception ở API.
- Validate input.
- Kiểm tra response format.
- Không để lỗi backend làm frontend crash.
- Không che giấu lỗi bằng try/except rỗng.
- Không xóa code cũ chỉ vì chưa dùng nếu chưa xác định nó không còn cần thiết.
- Không tạo file/module trùng chức năng.
- Giữ cấu trúc Backend đã thiết kế.

==================================================
QUY TẮC TEST
==================================================

Mỗi test case phải có:

| ID | Module | Test case | Input | Expected | Actual | Status | Bug ID |

Status:
- PASS
- FAIL
- BLOCKED

Không được ghi PASS nếu chưa thực sự chạy.

Sau mỗi lần sửa bug:
1. chạy lại test case gây lỗi
2. chạy các test case liên quan
3. kiểm tra regression
4. cập nhật kết quả.
